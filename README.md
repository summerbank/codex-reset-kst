# Codex Reset KST

[@codex_resets](https://t.me/codex_resets)의 초기화 공지를 읽어 UTC 시간을 한국시간(KST, UTC+9)으로 바꾸고, 사용자가 생성한 텔레그램 봇으로 개인 채팅·그룹·채널 중 선택한 곳에 알림을 보냅니다. Python + Telethon + SQLite를 사용하며 Linux 서버 또는 Docker를 지원하는 NAS의 Docker Compose에서 실행합니다. 서버에서 Telegram으로 연결하므로 외부 포트 개방은 필요하지 않습니다. GPU나 별도 AI API도 사용하지 않습니다.

```text
Codex 초기화 알림
상태: 발표
한국시간: 2026-10-16 14:00 KST
원문시간: 2026-10-16 05:00 UTC
원문: https://t.me/codex_resets/메시지번호
```

## 사용 방식

이 저장소의 코드를 내려받아 각자의 서버에서 실행하는 프로그램입니다. 사용자는 본인의 Telegram API ID/Hash, 알림 전용 봇 토큰, 사용자 계정 인증 세션을 준비해야 합니다. 저장소에 운영자의 인증정보나 공용 알림 서버는 제공되지 않습니다.

**실행 인스턴스 하나당 소유자 한 명과 알림 대상 한 곳**을 설정합니다. 기본 대상은 소유자의 개인 채팅이며, 소유자가 관리하는 그룹 또는 채널로 변경할 수 있습니다. 여러 그룹/채널을 독립적으로 운영하려면 각각 별도 봇과 별도 데이터 폴더를 사용해 설치하세요. 하나의 봇 토큰을 여러 서버에서 동시에 사용하지 마세요.

설치는 **API 정보 발급 → 봇 생성 → 환경변수 설정 → 사용자 계정 인증 → 컨테이너 실행 → 개인 채팅 등록** 순서입니다. 등록 후 텔레그램에서 `/ping`을 보내 실행 상태를 확인할 수 있습니다.

## 준비할 것

- Docker Engine, Docker Compose v2, Git이 설치된 Linux 기반 실행 환경. NAS에서는 Docker를 지원하는 컨테이너 관리 패키지를 설치합니다. 아래 명령은 실행할 서버의 터미널 또는 SSH에서 입력합니다.
- `git`, 텔레그램 사용자 계정과 앱, BotFather에서 만들 알림 전용 봇.
- 실행 서버에서 Telegram으로 나가는 HTTPS(443) 및 Telethon 연결이 허용되어야 합니다. 공유기에 포트를 열 필요는 없습니다.
- 로그인할 **사용자 계정으로** [원본 채널](https://t.me/codex_resets)에 가입하세요. 알림 봇을 원본 채널에 추가할 필요는 없습니다.

실행 서버에서 먼저 확인합니다.

```bash
docker --version
docker compose version
git --version
```

명령이 없거나 Docker 권한 오류가 나오면 서버의 패키지/관리자 설정에서 Docker, Compose v2, Git 및 실행 계정의 Docker 접근 권한을 설정하세요. 아래의 `docker compose` 명령은 모두 같은 프로젝트 디렉터리에서 실행합니다.

## 1. Telegram API ID / Hash 발급

1. 브라우저에서 [my.telegram.org](https://my.telegram.org)에 접속합니다.
2. 사용자 계정의 전화번호를 국가번호와 함께 입력합니다. 한국 번호는 `+82` 뒤에 국내 번호의 맨 앞 `0`을 제외한 번호를 입력합니다.
3. 텔레그램 앱으로 받은 로그인 코드를 입력합니다.
4. **API development tools**에서 애플리케이션을 만듭니다. App title과 Short name을 입력하고, 개인용으로 Platform은 Other 등을 선택합니다.
5. 발급된 **App api_id**(숫자)와 **App api_hash**를 보관합니다.

이 값은 BotFather의 봇 토큰과 다릅니다. 다른 사람이 운영하는 채널을 읽으려면 Telethon의 사용자 계정 로그인이 필요합니다.

## 2. 알림 봇 만들기

1. 텔레그램의 공식 [@BotFather](https://t.me/BotFather)를 엽니다.
2. `/newbot`을 보내고 안내에 따라 봇 표시 이름과 `bot`으로 끝나는 사용자명을 지정합니다.
3. 받은 토큰을 보관합니다. 예시 형식: `123456789:발급된_문자열`.
4. 생성한 **봇의 개인 대화**를 열어 Start 버튼 또는 `/start`를 보냅니다. BotFather 대화에 보내는 것이 아닙니다.

초기 `/start`만으로는 소유자를 등록하지 않습니다. 설치 후 `/start 등록코드`로 인증합니다. 이 봇은 이 프로그램 전용으로 사용하세요. 다른 프로그램의 `getUpdates`나 webhook과 함께 사용할 수 없습니다.

## 3. 저장소와 .env 준비

설치할 서버의 쓰기 가능한 폴더에서 실행합니다. 아래 명령은 현재 위치에 `codex-reset-kst` 프로젝트 폴더를 만듭니다. 특정 사용자명이나 서버의 절대 경로를 설정할 필요는 없습니다.

```bash
git clone https://github.com/summerbank/codex-reset-kst.git
cd codex-reset-kst
cp -n .env.sample .env
chmod 600 .env
vi .env
```

이미 저장소가 있으면 해당 디렉터리로 이동해 사용합니다. `cp -n`은 기존 `.env`를 덮어쓰지 않습니다. `vi` 대신 서버에서 제공하는 텍스트 편집기를 사용해도 됩니다. 다음 값을 실제 발급 정보로 바꿉니다.

```ini
TELEGRAM_API_ID=12345678
TELEGRAM_API_HASH=발급받은_API_HASH
BOT_TOKEN=BotFather에서_발급받은_토큰
SOURCE_CHANNEL=@codex_resets
BOT_REGISTRATION_SECRET=
BOT_CHAT_ID=
```

| 항목 | 필수 여부 | 설명 / 예시 |
| --- | --- | --- |
| `TELEGRAM_API_ID` | 필수 | my.telegram.org에서 발급된 양의 정수. 예: `12345678` |
| `TELEGRAM_API_HASH` | 필수 | 같은 화면에서 받은 API Hash 문자열. 예제 문구를 실제 값으로 교체 |
| `BOT_TOKEN` | 필수 | BotFather의 토큰 전체. 콜론 포함 |
| `SOURCE_CHANNEL` | 필수 | **`@`을 붙인 공개 채널 사용자명**. 예: `@codex_resets`. `https://t.me/...` 주소가 아님 |
| `BOT_REGISTRATION_SECRET` | 자동 등록 시 필수 | 아래 명령으로 생성하는 24~64자 영문/숫자/`_`/`-` 비밀코드. 자동 등록 후에도 `.env`에 유지 |
| `BOT_CHAT_ID` | 선택 | **소유자 개인 채팅의 양의 숫자 ID**. 예: `123456789`. 자동 등록 시 빈칸. 그룹/채널의 음수 ID나 `@username`은 여기에 넣지 않음 |
| `DATA_DIR` | 선택 | 로컬 Python 실행 시 상태 저장 폴더. 기본값은 코드 옆 `data/`. Compose는 `/app/data`로 지정하므로 `.env`에 추가할 필요 없음 |

`BOT_CHAT_ID`를 이미 아는 기존 사용자는 숫자를 유지하면 등록코드 없이 바로 사용할 수 있습니다. 저장된 소유자와 다른 숫자를 넣으면 시작을 거부합니다. 그룹/채널은 개인 소유자를 등록한 뒤 아래의 `/setgroup` 또는 `/setchannel`로 설정합니다. 소유자 ID와 알림 대상 ID는 별도로 저장되므로 `BOT_CHAT_ID`를 유지해도 그룹/채널 설정이 보존됩니다.

## 4. 이미지 빌드와 등록코드 생성

```bash
docker compose build
docker compose run --rm --no-deps monitor python monitor.py --generate-registration-secret
```

출력된 랜덤 문자열을 복사해서 `.env`의 `BOT_REGISTRATION_SECRET=` 뒤에 붙이고 저장합니다. 코드 생성 명령은 파일을 자동으로 수정하지 않습니다.

```bash
vi .env
```

코드를 채널, 그룹, GitHub, 스크린샷으로 공유하지 마세요. 누구든 이 코드를 먼저 사용하면 최초 소유자가 될 수 있습니다. 등록 이후에는 올바른 코드를 아는 다른 계정도 소유자를 덮어쓸 수 없습니다.

## 5. 사용자 계정 최초 인증

백그라운드 실행 전에 **한 번** 실행합니다. 이미 실행 중인 컨테이너가 있다면 먼저 중지합니다.

```bash
docker compose stop
docker compose run --rm monitor python monitor.py --login
```

프롬프트에 순서대로 입력합니다.

1. 사용자 전화번호: 국가번호를 포함한 본인의 실제 번호.
2. 텔레그램 앱 등으로 받은 로그인 코드.
3. 2단계 인증을 사용하면 계정 비밀번호. 입력 문자가 화면에 표시되지 않을 수 있습니다.

`Telegram user authentication saved`가 나오고 명령이 종료되면 성공입니다. 봇 토큰을 전화번호 프롬프트에 넣지 마세요. 인증코드와 비밀번호를 `.env`에 저장할 필요는 없습니다.

인증 세션은 프로젝트 폴더의 `./data/telegram_user.session`에 저장됩니다. `--rm`은 일회용 컨테이너만 제거하고 이 폴더는 남깁니다. 인증 중에는 모니터를 동시에 실행하지 마세요.

## 6. 백그라운드 실행과 개인 채팅 등록

```bash
docker compose up -d
docker compose logs -f --tail=100 monitor
```

`Watching @codex_resets`와 등록 대기 로그가 보이면, 생성한 봇의 **개인 대화**에서 `/start` 뒤에 공백과 4단계에서 만든 실제 코드를 붙여 보냅니다.

```text
/start 여기에_생성한_실제_등록코드
```

`개인 채팅 등록 완료!` 답장이 오면 끝입니다. Chat ID를 조회하거나 `.env`에 옮길 필요가 없습니다. 이후 `/start`만 보내면 소유자 등록 상태와 현재 알림 대상 종류를 확인합니다. 코드가 없거나 틀린 요청, 그룹 대화, 다른 계정의 등록 시도에는 응답하지 않습니다.

소유자 ID와 봇 업데이트 위치는 `./data/sent.sqlite3`에 보존됩니다. 컨테이너 재시작/이미지 업데이트 후에도 등록은 유지됩니다. 봇이 꺼져 있을 때 보낸 명령은 Telegram에서 최대 24시간 보관되므로, 응답이 없으면 모니터가 실행된 뒤 다시 보내세요.

로그 보기의 `Ctrl+C`는 로그 보기만 종료합니다. 서비스 상태는 다음으로 확인합니다.

```bash
docker compose ps
```

## 그룹 또는 채널로 알림 보내기 (선택)

먼저 6단계까지 진행하여 **소유자의 개인 채팅**을 등록합니다. 기존 사용자는 다시 등록하거나 데이터를 지울 필요가 없습니다. 이전 버전을 사용 중이면 먼저 업데이트합니다.

```bash
git pull --ff-only
docker compose up -d --build
```

1. Telegram에서 알림을 받을 그룹 또는 채널을 엽니다. 그룹은 구성원이 대화하는 공간이고, 채널은 구독자에게 게시물을 전달하는 공간입니다.
2. 생성한 알림 봇을 대상에 추가하고 **관리자**로 지정합니다. 채널에서는 봇의 **메시지 게시** 권한도 켭니다. BotFather에서 그룹 초대가 비활성화되어 있다면 `/setjoingroups`에서 허용합니다.
3. 소유자로 등록된 Telegram 계정도 해당 대상의 소유자 또는 관리자여야 합니다.
4. **봇과의 개인 대화**에서 대상 유형에 맞는 명령을 보냅니다. 아래 사용자명은 예시이므로 실제 대상의 공개 사용자명으로 바꿉니다.

그룹/슈퍼그룹:

```text
/setgroup @example_group
```

방송 채널:

```text
/setchannel @example_channel
```

공개 사용자명이 없는 대상은 사용자명 대신 `-100...` 등 실제 **음수 숫자 ID**를 사용할 수 있습니다. 초대 링크(`t.me/+...`)는 지원하지 않습니다. 공개 대상은 `https://t.me/example_channel` 링크의 마지막 부분에 `@`을 붙이면 됩니다. `SOURCE_CHANNEL`은 계속 원본 감지 채널을 가리키므로 변경하지 않습니다.

봇이 대상 유형, 봇의 관리자 권한, 등록된 소유자의 관리자 권한을 확인하고 **개인 대화로** 등록 완료 메시지를 보냅니다. 실패하면 기존 알림 대상을 유지합니다. 등록코드를 그룹이나 채널에 게시하지 마세요. 다른 구성원은 알림 대상을 변경할 수 없습니다. 관리자 확인은 [Telegram Bot API의 getChatMember](https://core.telegram.org/bots/api#getchatmember)를 사용하므로 이 프로그램은 봇의 관리자 등록을 요구합니다.

설정 이후 초기화 알림은 선택한 **한 곳으로만** 전송합니다. 이미 보낸 공지를 새 대상에 다시 보내지는 않으며, 전송 대기 중인 알림과 이후 공지는 새 대상으로 보냅니다. 대상 정보는 SQLite에 저장되어 재시작 후에도 유지됩니다. 그룹이 슈퍼그룹으로 전환되어 ID가 바뀌면 `/setgroup`으로 다시 지정하세요.

개인 채팅으로 알림을 되돌리려면 소유자가 봇과의 개인 대화에서 보냅니다.

```text
/setprivate
```

그룹 구성원은 설정된 그룹에서 `/ping` 또는 `/ping@봇사용자명`으로 실행을 확인할 수 있습니다. 봇이 여러 개 있는 그룹에서는 실제 봇 사용자명을 붙여 지정하세요. 다른 그룹의 명령에는 응답하지 않습니다. **채널 게시물의 명령에는 응답하지 않으므로 채널 운영자는 봇과의 개인 대화에서 `/ping`을 사용합니다.** 설정된 그룹/채널로 실제 메시지를 보낼 수 있는지는 다음 테스트 알림으로 확인하세요.

## 7. 실제 알림 전송 테스트

원본 채널의 새 공지를 기다리지 않고, 등록된 소유자가 **봇과의 개인 대화**에서 다음 명령을 보냅니다. 서버를 중지할 필요가 없습니다.

```text
/test
```

현재 설정한 개인 채팅·그룹·채널에 `[테스트] Codex 초기화 알림`이 전송됩니다. 그룹/채널이 대상이면 소유자의 개인 대화에도 전송 결과를 안내합니다. 테스트에는 UTC와 KST 시간이 표시되며, 원본 채널의 실제 공지가 아니라는 문구가 포함됩니다. 그룹이나 채널 게시물로 보낸 `/test`는 처리하지 않습니다.

테스트는 봇 전송과 대상의 게시 권한을 확인하며, 원본 채널의 새 메시지 감지 자체를 검증하지는 않습니다. 실제 공지 전송 기록·스캔 위치·대기열은 변경하지 않습니다.

서버 터미널에서 테스트하려면 다음 명령도 사용할 수 있습니다. 같은 세션을 동시에 열지 않도록 먼저 모니터를 중지합니다.

```bash
docker compose stop
docker compose run --rm monitor python monitor.py --test-notification
docker compose up -d
```

현재 설정한 알림 대상(개인 채팅·그룹·채널)에서 KST가 적힌 `[테스트] Codex 초기화 알림`을 확인하세요. 이 명령은 테스트 메시지만 보내며 채널 감지 자체를 검증하지는 않습니다. 실제 감지는 다음 원본 채널 공지가 올라왔을 때 원문 링크와 한국시간으로 확인합니다.

## 텔레그램에서 서버 실행 확인

등록된 소유자의 개인 대화 또는 설정된 그룹에서 다음 명령을 보냅니다. 서버 터미널에 접속하거나 모니터를 중지할 필요가 없습니다.

```text
/ping
```

서버에서 모니터가 실행 중이면 다음처럼 답합니다. `/status`도 같은 기능입니다.

```text
🏓 Pong! 모니터 프로세스가 실행 중입니다.
응답 시각: 2026-10-25 20:30:00 KST
```

응답은 Docker 컨테이너 안의 모니터 프로그램이 직접 보냅니다. 답장이 오면 해당 프로그램이 실행 중이고 Telegram과 왕복 통신할 수 있다는 뜻입니다. 서버 PC의 전원 상태를 별도로 조회하는 기능은 아닙니다. 소유자는 개인 채팅에서, 그룹 구성원은 현재 알림 대상으로 설정된 그룹에서 사용할 수 있습니다. 채널 감지와 초기화 알림 전체의 정상 동작까지 보장하는 검사는 아닙니다.

응답이 없다는 사실만으로 PC 전원 꺼짐, 컨테이너 중지, 프로그램 오류, 네트워크 장애를 구분할 수는 없습니다. 서버·컨테이너 상태와 봇 차단 여부, 개인 채팅 등록 여부를 확인하세요. 서버가 꺼져 있을 때 보낸 명령은 다시 켠 뒤 뒤늦게 응답할 수 있으므로 응답 시각을 확인하고, 지금 상태를 확인하려면 `/ping`을 새로 보내세요.

### 봇 명령어

| 명령 | 용도 | 사용 조건 |
| --- | --- | --- |
| `/start 등록코드` | 최초 개인 채팅 등록 | 올바른 비밀 등록코드 필요 |
| `/start` | 기존 등록 상태 확인 | 등록된 소유자의 개인 채팅 |
| `/ping` | 실행 중인 모니터의 응답 확인 | 소유자의 개인 채팅 또는 설정된 그룹 |
| `/test` | 설정된 알림 대상으로 테스트 메시지 전송 | 소유자의 개인 채팅 |
| `/status` | `/ping`과 동일 | 소유자의 개인 채팅 또는 설정된 그룹 |
| `/setgroup @사용자명` | 알림 대상을 그룹으로 변경 | 소유자의 개인 채팅, 대상 그룹의 관리자여야 함 |
| `/setchannel @사용자명` | 알림 대상을 채널로 변경 | 소유자의 개인 채팅, 대상 채널의 관리자여야 함 |
| `/setprivate` | 알림 대상을 소유자의 개인 채팅으로 복원 | 소유자의 개인 채팅 |

## 서버 터미널에서 연결 상태 진단

설정 후 또는 알림이 오지 않을 때 `--check`로 연결을 한 번에 확인할 수 있습니다. 같은 세션을 동시에 열지 않도록 서비스를 잠시 중지하고 실행합니다.

```bash
git pull --ff-only
docker compose build
docker compose stop
docker compose run --rm monitor python monitor.py --check
docker compose up -d
```

각 항목에 `[정상]` 또는 `[실패]`와 조치 안내를 출력합니다.

- 저장소: SQLite 무결성과 전송 대기 건수
- 사용자 세션: Telegram 연결, 사용자 계정 인증 여부
- 원본 채널: 방송 채널 여부, 가입 상태와 최신 기록 조회
- 알림 봇: 토큰 인증 및 Bot API HTTPS 응답, 저장된 봇과 일치 여부
- 봇 수신 설정: polling과 충돌하는 webhook 유무
- 알림 대상: 소유자 등록 여부 및 설정된 개인 채팅·그룹·채널 조회

사용자 연결 실패와 봇 연결 실패를 따로 확인하며, 응답이 없는 검사는 항목당 20초 뒤 실패로 처리합니다. 모든 항목이 정상이면 진단 명령의 종료코드는 `0`, 실패하거나 검사를 생략한 항목이 있으면 `1`입니다. 진단이 실패해도 마지막 `up -d` 명령으로 모니터를 다시 실행할 수 있습니다.

이 진단은 `/ping` 응답이 없거나 설정 오류를 자세히 확인할 때 사용하는 터미널 명령입니다. 로그인 코드를 요청하거나 알림을 전송하지 않고, 봇 업데이트를 소비하거나 채널 스캔 위치·대기열을 변경하지 않습니다. 모니터 프로세스 자체가 실행 중인지와 새 메시지 이벤트 수신 여부를 검증하는 명령은 아닙니다. 다른 polling 프로그램과의 충돌 및 봇 차단이나 그룹/채널의 게시 권한으로 인한 실제 전송 실패도 이 조회만으로 확정할 수 없습니다. `docker compose ps`, 로그, 테스트 알림 및 다음 원본 공지 수신을 함께 확인하세요.

## 운영 명령

재시작 (단순 프로세스 재시작):

```bash
docker compose restart monitor
```

`.env` 변경 적용 (restart만으로는 변경되지 않음):

```bash
docker compose up -d --force-recreate monitor
```

코드 업데이트:

```bash
git pull --ff-only
docker compose up -d --build
docker compose logs --tail=100 monitor
```

중지 / 다시 실행:

```bash
docker compose stop
docker compose up -d
```

현재 Compose는 `./data:/app/data` 바인드 볼륨을 사용합니다. 세션, 소유자 등록, 전송 기록, 전송 대기열이 모두 `./data/`에 남습니다. `data/`를 삭제하거나 빈 폴더로 교체하면 인증과 등록 및 중복 방지 기록이 사라집니다. 백업에는 `.env`와 `data/`를 함께 포함하고 외부 공개를 막으세요. SQLite 백업은 서비스를 중지한 상태에서 `data/` 전체를 복사하는 것이 안전합니다. Docker 로그는 파일당 10MB, 최대 3개로 회전합니다.

## 처리 규칙과 복구 범위

- `announced`는 발표, `expected`와 실제 채널의 `Possible Codex reset`은 예상, `confirmed`는 완료 확인으로 표시합니다. 공지 첫 번째 비어 있지 않은 줄만 파싱하여 인용문 속 다른 상태/날짜를 잘못 읽지 않습니다.
- 연도 없는 영문 날짜는 **원본 게시 시각(UTC)**에 가장 가까운 전년/당년/다음 해를 선택합니다. 연말·연초와 윤일을 처리하고, 180일 넘게 떨어진 모호한 날짜와 유효하지 않은 날짜는 무시합니다. 명시된 연도도 지원합니다. 수정 시각을 기준으로 연도를 바꾸지 않습니다.
- 시간이 없는 `confirmed`는 시간을 추정하지 않고 “시간 표기 없음”으로 알립니다.
- 같은 채널 메시지의 상태 또는 UTC 시간이 바뀌면 재알림합니다. 인용문/서식만 바뀐 수정은 재알림하지 않습니다. 아직 전송되지 않은 여러 수정은 최신 상태로 합칩니다.
- **처음 실행하거나 채널을 처음 바꿀 때 이전 공지를 일괄 전송하지 않습니다.** 그 시점 이후의 메시지를 추적합니다. 구버전에서 처음 업그레이드할 때도 같은 기준을 설정하고 기존 `sent` 기록은 보존합니다.
- 재시작/연결 복구 후 마지막 스캔 위치 이후의 새 게시물을 복구합니다. 60초마다 기록을 대조하고 최근 100개 메시지의 수정도 확인합니다. 초기 추적 기준 이전의 미전송 과거 공지는 제외합니다. 중단 중 수정된 100개 범위 밖의 과거 게시물은 복구를 보장하지 않습니다.
- 알림은 SQLite 대기열에 먼저 저장하고, 소유자 등록 전이나 전송 실패 시에도 남겨 둡니다. 일시 장애와 429 제한은 재시도하며 `retry_after`를 따릅니다. 봇 차단을 해제하면 대기 알림을 다시 시도합니다.
- 일반적인 중복은 채널 ID + 메시지 ID + 상태/시간으로 방지합니다. Telegram이 전송은 받았지만 응답이 유실되거나 전송 직후 DB 기록 전에 프로세스가 종료되면 드물게 중복될 수 있습니다. 엄밀한 “정확히 한 번” 전송은 보장하지 않습니다.
- 삭제된 원문을 조회해 이미 쌓인 대기 알림까지 취소하는 기능은 없습니다. 같은 메시지가 비공지로 수정된 것을 감지하면 대기열에서 제외합니다.
- 같은 `DATA_DIR`의 동시 프로세스는 잠금으로 거부합니다. 서로 다른 서버/폴더에서도 같은 봇으로 프로그램을 동시에 실행하지 마세요.

## 문제 해결

| 증상 | 확인할 내용 |
| --- | --- |
| `Missing` 또는 `.env에 ... 설정` | `.env.sample`이 아니라 `.env`를 편집했는지, 예제 문구를 실제 발급 정보로 바꿨는지 확인 |
| 자동 등록에 코드가 필요하다는 오류 | 4단계에서 코드를 생성하고 `.env`에 저장. 숫자 `BOT_CHAT_ID`가 있으면 코드 생략 가능 |
| 최초 인증 필요 | 서비스 중지 후 5단계 `--login` 실행. `.env`의 API ID/Hash는 사용자 계정용 값 |
| 입력 프롬프트가 보이지 않음 | SSH의 대화형 터미널에서 `docker compose run --rm ... --login` 실행. `up -d`로 최초 인증하지 않음 |
| 그룹/채널 등록 실패 | 봇과 소유자가 모두 관리자인지, 채널의 메시지 게시 권한이 켜졌는지 확인. 그룹은 `/setgroup`, 방송 채널은 `/setchannel` 사용 |
| `/ping`에 답하지 않음 | 컨테이너 실행 여부와 네트워크, 개인 채팅 등록을 확인. 원인 구분이 필요하면 `--check` 실행 |
| 봇이 `/start`에 답하지 않음 | 등록한 봇의 개인 대화인지, 서비스가 실행 중인지 확인. 최초에는 `/start 실제등록코드`가 필요. 등록 후에는 소유자의 `/start`만 응답 |
| `code=401` / `404` | BotFather 토큰 확인. 노출됐다면 BotFather에서 재발급 후 `.env` 수정 및 컨테이너 재생성 |
| `code=409` | 같은 봇의 다른 `getUpdates` 프로그램/컨테이너를 중지. webhook 설정 봇은 다른 서비스에 영향이 없도록 전용 봇으로 교체 |
| `code=403` / 전송 대기 | 봇 차단 해제 및 `/start` 전송. 저장된 소유자가 맞는지 확인 |
| `code=429` | Telegram 제한. 지정된 대기 시간 뒤 자동 재시도하므로 반복 재시작하지 않음 |
| 인증 취소 / 계정 인증 오류 | `docker compose logs --tail=100 monitor` 확인. Telegram 앱에서 세션이 취소됐다면 서비스 중지 후 `--login` 재실행 |
| 연결/스캔 재시도 | 실행 서버의 DNS, 시간 동기화, 방화벽, 인터넷 및 Telegram 접근 확인. 일시 오류는 재시도하고 연결 종료 시 Compose가 재시작 |
| 새 알림이 없음 | 첫 실행은 과거 공지를 보내지 않음. 동일 사용자 계정의 채널 가입, `SOURCE_CHANNEL=@codex_resets`, 등록 확인 답장, 원문 신규 공지 확인 |
| DB 잠금 / 동시 프로세스 오류 | `--login` 또는 테스트 실행 전에 `docker compose stop`. 동일 `data/`를 쓰는 다른 컨테이너가 없는지 확인 |
| Permission denied | 프로젝트 폴더/마운트 접근 권한 확인. 컨테이너가 만든 `data/` 파일은 호스트에서 root 소유일 수 있음. `chmod 777`로 공개하지 않음 |
| `.env`를 바꿨는데 그대로 | `docker compose up -d --force-recreate monitor` 실행 |

소유자 또는 봇을 바꿔야 한다면 기존 등록을 덮어쓰거나 DB를 지우지 말고, 서비스를 중지한 뒤 기존 데이터를 별도 폴더에 보관하세요. **아래는 의도적으로 소유자를 새로 등록하려는 경우에만** 실행합니다. 이미 `data.previous`가 있으면 먼저 다른 백업 이름을 정하세요.

```bash
docker compose stop
mv -n data data.previous
```

`.env`에서 새 봇/등록코드를 설정하고 `BOT_CHAT_ID`를 비운 다음, 5~7단계를 다시 진행합니다. 새 데이터 폴더이므로 사용자 계정 인증도 다시 필요하며 이전 공지는 가져오지 않습니다. 기존 인증 파일을 GitHub나 채팅으로 전달하지 마세요.

## 개발 및 검증

Python 3.12 이상과 Linux 환경에서 실행합니다. 운영 이미지는 Python 3.12를 사용합니다. 테스트는 실제 Telegram 접속이나 `.env` 읽기 없이 파서, DB, 비밀코드 등록, API 모형을 검증합니다.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m unittest discover -s tests -v
```

Docker와 같은 Python 3.12 환경에서도 확인할 수 있습니다.

```bash
docker compose build
docker run --rm --entrypoint sh -v "$PWD/tests:/tests:ro" codex-reset-kst-monitor -c 'python -m unittest discover -s /tests -v'
```

`.env`, `*.session*`, SQLite 파일과 `data/`는 Git 및 Docker 빌드 컨텍스트에서 제외합니다. 로그에 Bot API URL/토큰이나 인증코드를 출력하지 않습니다. 세션 파일은 계정 접근 권한을 가진 민감정보로 취급하세요. 커밋 전에는 `git diff --cached`로 민감정보가 없는지 확인합니다.

프로토콜 참고: [Telegram Bot API](https://core.telegram.org/bots/api#getupdates), [Telethon 클라이언트 문서](https://docs.telethon.dev/en/stable/modules/client.html). 원본 채널 문구가 바뀌면 파서 업데이트가 필요할 수 있습니다.
